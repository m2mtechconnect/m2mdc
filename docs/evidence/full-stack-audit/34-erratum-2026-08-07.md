## 1. F-02 - WITHDRAWN AS WRITTEN, DOWNGRADED

**Stage 1 claim (withdrawn):** "45+ UPDATE policies lack WITH CHECK - a user may rewrite ownership columns."

**Correction.** PostgreSQL applies the `USING` expression as the effective `WITH CHECK` expression when
`WITH CHECK` is omitted for `UPDATE` (and for `ALL`). Omission alone therefore proves nothing about
ownership-column rewriting. The Stage 1 finding conflated syntax with effect.

**Re-analysis.** Every `UPDATE` and `ALL` policy in `public` was re-enumerated with its explicit and effective
check expression, its role scope, its permissive/restrictive class and the other policies applicable to the
same table and command. Permissive policies were composed with OR; restrictive policies with AND.

Evidence: `24-f02-update-policy-effective-check-matrix.csv`

| Measure | Value |
|---|---|
| UPDATE/ALL policies in `public` | 69 |
| Policies with no explicit `WITH CHECK` | 53 |
| Policies whose effective `WITH CHECK` is inherited from `USING` | 53 |
| Policies whose effective check does not constrain ownership, a role predicate or a parent subquery | 16 |
| ...of those, reachable by `anon` or `authenticated` | 0 |
| **Statically proven ownership-rewrite bypass** | **0** |

All 16 unconstrained effective checks belong to policies scoped `TO service_role`. `service_role` bypasses RLS
by design and is not reachable from a browser client; those policies cannot be exercised by an application
principal. The two literal `USING (true)` policies (`copilot_memory`, `oauth_states`) are both
`TO service_role`.

For all client-reachable policies, the inherited effective `WITH CHECK` re-evaluates the same ownership
predicate (`auth.uid() = user_id`, `auth.uid() = owner_id`, `created_by_user`, `deployed_by`, `invited_by`, or a
parent-ownership subquery) against the *resultant* row. A principal cannot therefore hand a row to another
principal or steal one through these policies on static analysis.

**Revised finding.** F-02 is downgraded from HIGH to **MEDIUM - hardening recommendation**:
*"53 UPDATE/ALL policies rely on implicit WITH CHECK inheritance."* Implicit inheritance is correct today but
is a latent maintenance hazard: any future widening of `USING` (for example to add an admin read path) would
silently widen the write post-image at the same time. Recommendation: author explicit, operation-specific
policies so read scope and write post-image are independently reviewable.

**Residual uncertainty.** This is a static conclusion. `runtime_test_required = yes` is recorded for all 53
client-reachable policies; authenticated UPDATE-escape probes remain blocked pending the disposable project.

## 2. F-01 - RE-PROVEN, REMAINS CRITICAL, WORDING CORRECTED

**Stage 1 claim (imprecise):** "No tenant isolation model - only 14 of 113 tables carry a tenant/org column."

**Correction.** Column counting is not a proof. Every one of the 113 `public` tables was reclassified and each
tenant-owned resource had its authoritative ownership path traced through direct columns, foreign keys to
parents (to depth 4), and the policy set.

Evidence: `25-f01-resource-tenant-classification.csv`

| Classification | Tables |
|---|---|
| tenant_owned (direct tenant/org column, or inherited from a tenant-scoped parent) | 26 |
| user_private (scoped to `auth.uid()` directly or via parent) | 60 |
| deliberately_public (catalogs, templates, funding programs, locations) | 10 |
| system_internal (caches, logs, audit, heartbeats) | 7 |
| unknown (no ownership column, no ownership FK, policy intent unclear) | 10 |
| platform_global | 0 (none identified) |
| **Total** | **113** |

Tables with a *direct* tenant/org column: **13**. The remaining tenant_owned tables inherit through a parent.

**Core resource graph.** 49 tables were identified as core (facilities, twins, assets, telemetry, simulations,
recommendations, agents, integrations, DSX). Of those, **16** resolve to a tenant path; **33** resolve only to a
per-user path, and 5 (`agent_environments`, `agent_suggestions_cache`, `agent_templates`,
`dc_blueprint_templates`, `recommendations`) resolve to **no ownership path at all**.

The authoritative facility/twin table `public.data_centre_twins` carries `created_by_user` and `location_id`
only. It has no `tenant_id`, no `org_id`, and no foreign key to `public.organizations`. Its ownership is
per-creator, not per-tenant.

**Revised wording (precise):**

> **Multi-tenant isolation is not implemented for the core resource graph.** Facilities, twins, telemetry,
> simulations, recommendations and integrations have no non-forgeable tenant ownership path; access is scoped to
> the individual creating user, and any tenant-level sharing would today require widening policies to
> role-based or open predicates.

The stronger claim *"the schema cannot express tenant ownership"* is **NOT** made and is not supported.
`public.organizations` exists, `public.profiles.org_id` exists, and 13 tables already carry a tenant/org
column. The schema can express tenant ownership; the core graph simply does not use it.

**Severity: CRITICAL, unchanged.** The trigger condition in the erratum instruction is met: core facilities,
twins, telemetry, simulations, recommendations and integrations lack a non-forgeable tenant ownership path.

## 3. F-04 - TERMINOLOGY CORRECTED, DOWNGRADED

**Stage 1 claim (withdrawn):** "107 of 157 Edge Functions are orphaned."

**Correction.** Absence of a repository caller does not establish that a deployed function is unreachable.
Frontend invocations, function-to-function calls, database webhooks and triggers, scheduled jobs, queues,
external provider callbacks, public API consumers, deployment configuration and runbooks were inspected.

Evidence: `26-f04-edge-function-reachability.csv`

| Reclassification | Count |
|---|---|
| active_internal (frontend invocation or function-to-function call found in repo) | 89 |
| callback_or_webhook (signature/OAuth/callback protocol surface present) | 6 |
| scheduled | 0 identified in repo configuration |
| active_external | 0 established (external reachability not observable from the repository) |
| legacy_candidate | 0 asserted |
| **no_in_repo_caller** | **61** |
| unknown | 0 |
| **proven_orphan** | **0** |

**Revised finding.** F-04 becomes: *"61 Edge Functions have no in-repository caller; external and operational
reachability has not been excluded."* Severity downgraded HIGH -> **MEDIUM**. The number **107 is withdrawn**;
it double-counted functions reachable only through function-to-function calls and protocol callbacks.

The underlying concern - an unreviewed deployed surface - stands, and is reinforced by the new static scan
(`28-edge-function-static-security-scan.csv`): 80 of 156 functions emit a wildcard CORS origin, 79 contain no
authorization check, 33 use the service-role key, 10 log values whose identifiers suggest credential material,
and 2 functions have `verify_jwt = false` in `supabase/config.toml`. Those are tracked as new finding **F-13**.

**Prerequisite before deletion:** production invocation logs per function over a 30-day window. No function may
be classified `proven_orphan` on repository evidence alone.

## 6. Tightened claims

**F-11 (anon surface).** The Stage 1 sentence "anon holds exactly one privilege" is now correctly scoped and
extended. Table, schema, sequence, function, view, Storage and RPC privileges were all enumerated
(`31-anon-privilege-inventory.csv`):

- Table privileges: exactly one - `INSERT` on `public.onboarding_submissions`. Zero privileges on the other 112 tables.
- Schema: `USAGE` on `public`, `storage`, `graphql_public`; no `CREATE`.
- Sequences: none.
- Functions: `EXECUTE` on 129 functions in `public`. 126 are pgvector extension operator functions; 2 are
  `SECURITY DEFINER` trigger functions (`on_profile_approved_grant_default_role`,
  `on_profile_approved_provision_twin`) which return `trigger` and are not RPC-callable; 1 is
  `public.match_documents`, which is `SECURITY INVOKER`, so RLS and the (absent) anon table grants still apply.
  The audited `admin_*` role RPCs have `EXECUTE` revoked from `anon`.
- Storage: one public bucket, `profile-images`, public-read by design; no anon write policy on `storage.objects`.

Revised statement: *"anon holds exactly one table privilege (INSERT on onboarding_submissions) and no
privilege-escalating function, sequence or Storage write path was identified by static enumeration."*
Runtime anon probes remain outstanding. F-11 stays INFORMATIONAL, with the `EXECUTE` breadth on `public` noted
as a hardening item (revoke default `EXECUTE` from `anon` on `public` and grant per-RPC).

**F-08 (no server/queue/worker tier).** The absence of a tier is architecture, not a defect in itself.
Severity is retained at HIGH only because it is now tied to concrete failure modes observed in the codebase:

1. **Durability.** Simulation and ingest runs are driven from the browser; a tab close or reload mid-run leaves
   `*_runs` rows in a non-terminal state with no reconciler to advance or fail them.
2. **Availability.** Supabase Edge Functions have a bounded wall-clock budget; long crawl/ingest/analysis paths
   have no continuation mechanism and fail at the boundary rather than resuming.
3. **Workflow.** There is no retry, backoff, idempotency key or dead-letter path for any external integration
   call, so a transient provider failure is a permanent data gap with no operator-visible queue.

If those three conditions are not accepted as pilot-blocking, F-08 should be re-rated MEDIUM. It is not rated
HIGH merely for lacking a tier.

**Readiness score.** The 39% figure is marked **PROVISIONAL** wherever it appears. It cannot be finalised until
the corrected F-01/F-02/F-04 severities and the blocked-versus-unblocked gate split are reflected in a
re-scored matrix; the recomputed provisional figure is **43%**, and the verdict is unchanged.
